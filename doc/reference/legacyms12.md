SRB2 Legacy API ("MasterServer v1.2")
=====================================

This document attempts to reconstruct the binary master server API that has
been in use by SRB2 Final Demo v1.0.9 (referred to as "MasterServer v1.2").
For reference, the files `mserv.c` and `mserv.h` of have been consulted,
which are free to audit under the GNU General Public License version 2.

The legacy master server API is implemented in the game client as a UDP/IP socket protocol set
up upon the default UDP port of `:28900`.

Unlike it's HTTP-based successor, the legacy master server API does not
appear to logically partition it's netgames into rooms. Instead, all
interaction after initial connection with the legacy master server can be
deduced from the non-static function names defined in `mserv.h`:

- Register netgame
- Unregister netgame
- Tick (send a keep-alive signal to prevent your netgame from being culled)
- Fetch netgame lists

Netgame list fetch
------------------

When fetching netgame lists, the client first defines an array of netgame
entry structs (max. 10 netgames) and proceeds to connect to the configured
master server.

The message packet that's being sent to the master server seems to have the
following structure:

         +----------------------------+
    0x00 | unused padding             |
         +----------------------------+
    0x04 | GET_SHORT_SERVER_MSG (205) |
         +----------------------------+
    0x08 | (long) length              |
         |  = entry + HEADER_SIZE     |
         |    (+++)      (12B)        |
         +----------------------------+
    0x0C | no buffer                  |
         |                            |
         +----------------------------+
                     [0x0C]

After receiving, parsing and cleaning up it's received netgame listing
status, the client closes the previously established UDP connection. Most
likely, the server response will look something like this:


         +--------------------------------+
    0x00 | (unused padding)               |
         |                                |
         |                                |
         |                                |
         +--------------------------------+
    0x04 | (unknown code, maybe 0=OK)     |
         +--------------------------------+
    0x08 | autogenerated length           |
         |  = entries + HEADER_SIZE       |
         |     (var)       (12B)          |
         +--------------------------------+
    0x0C | array of netgames entries      |
         |                                |
         +--------------------------------+
                   [0x58 - ???]


Netgame registration
--------------------

Upon registration, the client opens a UDP socket

For netgame deregistration, the client first sets up a UDP connection to
the master server and then sends the following packet before quietly
closing the connection:

         +----------------------------+
    0x00 | unused padding             |
         |                            |
         |                            |
         |                            |
         +----------------------------+
    0x04 | ADD_SERVER_MSG (101)       |
         +----------------------------+
    0x08 | (long) length              |
         |  = entry + HEADER_SIZE     |
         |    (80B)      (12B)        |
         +----------------------------+
    0x0C |       +----------------+   |
         |  0x0C | NUL            |   |
         |       +----------------+   |
         |  0x18 | NUL            |   |
         |       +----------------+   |
         |  0x28 | client port    |   |
         |       +----------------+   |
         |  0x30 | netgame name   |   |
         |       +----------------+   |
         |  0x50 | client version |   |
         |       +----------------+   |
         |                            |
         +----------------------------+
                     [0x58]


After the server registration completed (successfully or unsuccessfully),
the UDP socket is closed.


Netgame deregistration
----------------------

For netgame deregistration, the client first sets up a UDP connection to
the master server and then sends the following packet before quietly
closing the connection:

         +----------------------------+
    0x00 | unused padding             |
         +----------------------------+
    0x04 | REMOVE_SERVER_MSG (103)    |
         +----------------------------+
    0x08 | (long) length              |
         |  = entry + HEADER_SIZE     |
         |    (80B)      (12B)        |
         +----------------------------+
         |       +----------------+   |
    0x0C |  0x0C | NUL            |   |
         |       +----------------+   |
         |  0x18 | NUL            |   |
         |       +----------------+   |
         |  0x28 | client port    |   |
         |       +----------------+   |
         |  0x30 | netgame name   |   |
         |       +----------------+   |
         |  0x50 | client version |   |
         |       +----------------+   |
         +----------------------------+
                     [0x58]

As you can see from the lack of IP within the payload, it is very likely
that the original legacy master server used the issuer's IP address to
identify netgame listing candidates. Regardless, as LiquidMS already uses
this mechanism within it's V1 API implementation for verification purposes,
it naturally extends this policy towards it's legacy API implementation.


Master Server Tick
------------------

Much like v1's POST endpoint `/<serverid>/update`, the legacy API relies on
a regular keep-alive signal supplied by the client to determine whether a
netgame listing is deprecated and worth culling. On behalf of the game
client, the frequency of the keep-alive signal has been hardcoded to
a span of two seconds.

Messages
--------

MasterServer v1.2 messages are made up of the following 8-byte-aligned fields:

         +--------------------+
    0x00 | (long) id          |
         +--------------------+
    0x04 | (long) type        |
         +--------------------+
    0x08 | (long) length      |
         +--------------------+
    0x0C | (char) buffer      |
         |   ... (max. 1024B) |
         +--------------------+

Netgame entries are defined by the following structure:

         +----------------+
    0x00 | (char) header  |
         | (probably raw) |
         +----------------+
    0x0C | (char) ip      |
         +----------------+
    0x1C | (char) port    |
         +----------------+
    0x24 | (char) name    |
         +----------------+
    0x44 | (char) version |
         +----------------+
                [0x4C]
